## Context

See `proposal.md` for motivation and `specs/queue-cancellation-and-dismissal/spec.md` for the observable contract. Queue path groups use the lexical parent of a normalized media path, while batch cards are keyed by batch ID. The implementation must retain running ownership through process-tree exit and keep filesystem cleanup under the Housekeeping engine.

## Goals / Non-Goals

**Goals:** preserve active ownership until worker acknowledgment, support exact path-group removal across batches, keep dismissal bounded to database work, and expose cleanup outcomes.

**Non-Goals:** add a new QueueJob status, change completed/Validation/Publisher dismissal policy, follow symlinks to infer path identity, or remove source/Library files.

## Decisions

1. **Persist cancellation request without changing the public job status.** Add `cancellation_requested_at` while a job remains `running`. A queued job transitions directly to `canceled`; the same transaction releases its Scheduler reservation. A running job retains its reservation and active lifecycle projection until the worker acknowledges a terminal result after its direct FFmpeg process group exits. On Darwin/Linux, MVForge starts FFmpeg in a dedicated process group, kills the group on cancellation, and waits up to ten seconds for group absence before unregistering the process or releasing the reservation. That monitor persists `process_tree_exit_verified_at` with the terminal transition. If cancellation arrives after the monitor's preliminary Queue read, the final exit transaction still persists verified process-tree evidence atomically with terminal `canceled`, reservation release, and cleanup intent. Other callbacks can report terminal state but cannot authorize cleanup for a started job without this evidence. Unsupported platforms refuse FFmpeg launch, and cleanup of previously started jobs fails closed where process-tree containment is unavailable. A process group that cannot be verified remains active and blocks cleanup/requeue. The execution path does not launch a shell wrapper; a descendant that deliberately escapes the process group remains outside the verified contract and is NO-GO. Compare-and-update checks prevent stale cancellation requests or callbacks from overwriting a newer state. GORM AutoMigrate adds the nullable request field; existing rows remain unchanged.

2. **Derive path-group identity the same way as Queue display.** Normalize separators and compare the exact lexical parent group key of `QueueJob.MediaPath`; the special `Root` group follows the existing Queue helper. A prefix query may narrow candidate rows, but every preview and mutation rechecks exact group equality. The operation never resolves or mutates filesystem paths. Preview scans at most 10,000 candidate rows and returns at most 500 stable IDs in ID order; confirmation sends at most 500 selected IDs. One transaction uses compare-and-update for each ID and reports already-dismissed, skipped, and conflicted outcomes. Never-executed placeholders are soft-dismissed so retries can report them as already dismissed; their unused ExecutionPlans are removed.

3. **Persist cleanup ownership and let Housekeeping execute it.** When a newly canceled job is eligible under the current cancellation policy, the same QueueJob transaction stores one stable operation ID, frozen output target, cancellation revision, `pending` state, and empty lease before the terminal transition is acknowledged. This database write performs no filesystem mutation. The existing Housekeeping worker reconciles legacy `pending`/`running`/`failed` rows that lack an operation ID, claims work with a compare-and-update lease token and expiry, and executes only after claim. The claim query filters eligible, due work before applying its 64-row bound, so capped, leased, and not-yet-due rows cannot starve later operations. The five-attempt budget counts failed or interrupted executions; ownership deferrals have a separate durable count and capped exponential schedule (15 seconds through 5 minutes), remain visible in cleanup diagnostics, and do not consume that budget. It recovers expired claims after restart and fences every completion and pre-delete check with the current token. Empty legacy cleanup state remains ambiguous and is not backfilled. Before execution it revalidates the QueueJob status/revision/output target, current policy, configured `work` root, tree/file identity, active process, reservation, and existing Housekeeping references. Deletion uses Housekeeping path resolution, symlink checks, tree identity, and removal helpers; no roots are added. Lease loss, active ownership, changed identity, or unsafe paths fail closed. Dismissal never waits for filesystem work.

4. **Use one Queue-level preview/confirm flow for path removal.** Add preview and dismiss API operations accepting the exact path-group key and optional selected IDs. The UI can start the flow from any eligible canceled row, display backend counts/reasons and selectable candidates, then send one bounded dismiss request. Batch removal remains available with its all-canceled predicate. Both flows invalidate Queue and Assets once after the response.

5. **Measure database dismissal separately from cleanup.** Add focused tests/benchmarks for 1, 25, and 100 canceled records with an injected slow cleanup barrier. The API must complete while the cleanup barrier is blocked; report measured local database times as test evidence and do not claim NAS benchmark results. A five-run, 30-request-per-run comparison on the development host measured median SQLite HTTP request times of 0.599 ms / 5.553 ms / 19.912 ms for the baseline batch-dismiss endpoint and 0.377 ms / 4.527 ms / 17.690 ms for the new exact-path endpoint (1 / 25 / 100 records), reductions of 37% / 18% / 11%. Each benchmark seeds synthetic rows outside the timer. The baseline uses the existing batch API and the new path API uses the same canceled row counts; artificial slow cleanup is covered by a separate blocked-cleanup regression, not by the timing benchmark. These local in-memory SQLite measurements exclude NAS I/O, real filesystem cleanup, asset catalog scans, and browser rendering; they are not NAS or end-to-end latency claims.

## Risks / Trade-offs

- [A stale worker callback could race a cancellation request] → compare state inside the transaction and let the worker's final status own completion; keep the reservation while cancellation is pending.
- [A cleanup process could outlive its lease] → require token and unexpired lease at each destructive boundary, renew during Housekeeping work, and refuse stale completion; expired claims are revalidated before a new token is issued.
- [A process could outlive its FFmpeg leader] → place direct FFmpeg in its own process group and retain worker ownership until the group is absent; escaped descendants or unsupported execution wrappers remain NO-GO and cannot authorize cleanup.
- [Queue path display is lexical, not filesystem-resolved identity] → use the same stable key for UI and backend, exact equality after candidate lookup, and no filesystem mutation in path dismissal.
- [Large paths could exceed a single safe request] → cap preview candidates and require the operator to confirm the returned bounded set; accept an explicit selected-ID subset.

## Migration Plan

Add a nullable cancellation-request timestamp and QueueJob cleanup operation/lease fields through the existing AutoMigrate path. Existing `pending`/`running`/`failed` rows from the process-local implementation are adopted by Housekeeping with a deterministic operation ID after current policy and ownership checks. Legacy rows with empty cleanup state are left untouched because their original policy authorization is unknown. Rollback keeps the added columns; older binaries ignore them and continue reading existing Queue fields.
