## Architecture and contract

The existing Queue dismissal remains the sole owner of the transactional lifecycle change. `QueueHandler.Dismiss()` and `validateCompletedValidationDismissal()` retain their eligibility, CAS, reservation release, publisher exclusion, history, and idempotency behavior; neither gains filesystem side effects. Validation coordinates two explicit operations: issue a short-lived, single-job preview; commit the existing Dismiss; then, only when selected and the Dismiss response is successful, consume the preview in a separate Housekeeping operation. A cleanup error is a cleanup result, never a Dismiss error.

### HTTP API

- `POST /api/validation/jobs/:id/staging-cleanup/preview` accepts an empty body. It is available for a current eligible Validation exception and for an already dismissed eligible job with retained/failed/blocked staging. It returns `jobId`, `executionNumber`, `validationRunId`, `previewId`, `expiresAt`, `state` (`ready`, `blocked`, or `noop`), `workspacePath`, `ownership`, `reason`, `files` (`path`, `sizeBytes`, `kind`), `totalBytes`, and `blockers`. Paths are server-derived, rooted in the resolved Work role, and displayed for operator inspection.
- `POST /api/validation/jobs/:id/staging-cleanup` accepts `{ "previewId": "..." }`. It only consumes that token for that route job after Dismiss is durable. It returns `jobId`, `previewId`, `outcome` (`cleaned`, `noop`, `blocked`, or `failed`), `removedPaths`, `recoveredBytes`, `reason`, and the appended evidence ID. A stale, mismatched, expired, or already-consumed token returns conflict with the durable latest outcome when one exists. Unsafe cleanup itself returns a successful Dismiss-independent outcome so clients can distinguish it from Dismiss failure.
- Existing Dismiss API shape and route remain unchanged. No cleanup choice or path is accepted by Dismiss.

The preview endpoint never writes `housekeepingPreview` or its report and does not call the general Preview/Execute APIs. Its token is stored in an independent preview table, never in the singleton general Housekeeping setting. `ValidationHistorySummary` gains `stagingState` (`retained`, `cleaned`, `failed`, `blocked`, `no_workspace`, `not_applicable`), `stagingCleanupOutcome`, `stagingCleanupReason`, `stagingRecoveredBytes`, and `stagingCleanupAt`. Batched queries load the latest evidence and unconsumed preview state for a History page; no per-job request is added. History's Review/Retry action requests a fresh preview and presents the same dialog before confirmation.

## Eligibility and canonical identity

The backend loads `QueueJob` by its primary ID and reuses the exact current Dismiss validation gate, including the frozen ExecutionPlan, ResultArtifact and canonical ValidationRun/finding binding. The persisted QueueJob ID selects only the exact direct child `work/job-<QueueJob.ID>`; `ExecutionNumber` is display and identity evidence, never a workspace selector. The workspace must be a real direct directory under `StorageRoleWork`, have an unambiguous job owner, and contain `OutputPath` when the database records one. The complete normalized storage-role set is loaded on every preview and execution. Work overlapping RAW, Library, or Originals Archive blocks cleanup.

Preview records a manifest sorted by relative path. Each entry must be a regular file or directory; links, special files, unreadable entries, traversal, noncanonical names, and case/normalization ambiguity block cleanup. The snapshot binds QueueJob ID/status/dismissal timestamp, ExecutionNumber and ExecutionPlan ID/version/fingerprint, Result artifact ID/generation/output revision, ValidationRun ID/outcome, exact output path, Work root and workspace paths, directory-tree identity, file manifest and byte total, and active-reference check time. Missing/ambiguous persisted identity blocks cleanup; an absent workspace is an explicit zero-byte no-op.

Before consumption, the service re-reads and revalidates those identities and requires the job's Dismiss timestamp to be durable. It checks the complete current ownership surface: job/process lifecycle, reservation rows, active Queue state, maintenance operations and their paths, Publisher publications/attempts/leases, Test Encode ownership/artifacts, preview/sidecar/artifact references, and other Queue jobs whose persisted paths overlap the workspace. Any query/table/check error is a blocker. A dismissed completed job's historical protection is bypassed only for this exact token and only after the normal current Dismiss gate and all other references pass. `isProtectedHousekeepingJob()` remains unchanged for global and automatic Housekeeping.

## Housekeeping integration and filesystem safety

The scoped operation builds exactly one `job_workspace` `HousekeepingCandidate` using the existing ownership classification, role/path resolution, tree identity, byte accounting, active-reference machinery, and `executeHousekeepingCandidate` deletion path. The engine is extended with an explicit, unforgeable internal authorization context derived from the consumed persisted token; normal candidate execution continues to use the current general policy and protection rules. It never calls `ExecuteHousekeepingPreview()` and cannot enumerate or include unrelated candidates. The candidate's expected job ID, path, reason, identity, files and bytes are checked again at the deletion boundary.

Deletion is serialized per QueueJob within the process, while a database transaction consumes the one-time token and fences concurrent cleanup attempts. The filesystem path is opened as a rooted directory using Go's `os.Root` APIs. The implementation traverses and removes only manifest entries by relative path, refuses symlinks and special files at every component, re-stats each opened entry immediately before unlink, and removes directories only after they are empty. It does not call `os.RemoveAll` on a path whose tree was merely hashed. Rooted operations prevent traversal or symlink escape; inode/type/size checks detect replacements, and only the previewed names are candidates for removal. On any change or failure the walk stops, records only entries actually removed, and retains all untouched or newly added entries. Filesystem and SQLite cannot share an atomic transaction, so a crash after partial deletion is represented as a failed/partial attempt; a new preview binds the remaining tree and retry is idempotent. General application writers are excluded by active-reference gates and per-job serialization; uncoordinated out-of-band filesystem mutation is still detected entry by entry and never expands deletion beyond the rooted manifest.

## Persistence and migration

Add two SQLite models via the normal `database.Migrate` auto-migration path:

- `ValidationStagingCleanupPreview`: random opaque token ID, QueueJob ID, captured immutable identity/role/path/manifest JSON, byte count, creation/expiry, consumed timestamp, and outcome/evidence reference. Rows are independent from global Housekeeping preview state. Consumed or expired rows are retained as audit/fencing context; there is no destructive cleanup job on startup.
- `ValidationStagingCleanupEvidence`: append-only event rows with QueueJob ID, ExecutionNumber/ExecutionPlan and Result/Validation identities, preview ID and preview tree identity, server-resolved actor, action (`dismiss_cleanup` or `history_retry`), event (`started` or `completed`), outcome, event timestamp, removed relative paths, actual recovered bytes, and blocker/error reason. Application code only inserts evidence; SQLite triggers reject updates/deletes. A `started` row precedes filesystem work and the terminal `completed` row records actual progress. If the process stops after partial removal, the durable `started` row has no terminal completion; History presents it as failed/blocked, and retry requires a fresh preview of the remaining workspace. Latest state derives from the latest terminal evidence row; prior outcomes are never overwritten by Housekeeping runs.

No historical backfill is required. Existing dismissed jobs without evidence report `retained` if an owned workspace is present, otherwise `not_applicable`/`no_workspace`; they are not automatically cleaned. Existing database startup adds empty tables and leaves Queue, Results, Validation, and Publisher data untouched. The actor comes from the server's authenticated/local operator context, never a client-supplied field.

## UI behavior

Validation's Dismiss action opens a compact dialog and starts the read-only preflight. The optional “Also clean staged output” checkbox starts checked; while preview loads it is disabled. The dialog shows QueueJob ID separately from execution number, workspace ownership/reason, file names and sizes, total bytes, and blocker text. A blocked preview disables cleanup but leaves the Dismiss button available. Confirmation always performs Dismiss first; only a committed Dismiss with the checkbox selected calls the scoped cleanup API. The dialog/result state explicitly reports “Dismissed; staging retained” or the cleanup outcome, never a false Dismiss failure.

History displays a distinct staging chip/summary and uses the same preview dialog for Review staged files or Retry cleanup. Retry requires fresh explicit confirmation. A cleaned workspace is shown as physically unavailable while Validation/Result detail remains available from persisted evidence. Existing Queue Dismiss controls remain lifecycle-only and do not implicitly request cleanup.

## Testing and resource impact

Backend tests use temporary Work roots and disposable SQLite databases. They cover exact files and bytes, no-op absence, symlink rejection, changed manifests, active reservation and other-job sidecar blockers, concurrent token consumption, Dismiss/cleanup sequencing, partial removal accounting with a fresh-manifest retry, append-only database triggers, preservation of RAW/report/Validation evidence, and isolation from global Housekeeping. Frontend tests cover default-on opt-in, blockers while retaining Dismiss, checkbox-off behavior, cleanup failure after successful Dismiss, and History retry. The scan is bounded to one job workspace and runs only after an explicit preview; it adds no periodic filesystem work or media processing. No NAS is contacted by tests.

## Risks and tradeoffs

- SQLite and filesystem work cannot commit atomically. Durable started/completed evidence plus re-previewed retry makes partial progress visible without pretending rollback occurred.
- The general Housekeeping candidate path currently removes a workspace with `os.RemoveAll`; explicit cleanup must extend the existing engine boundary with rooted, manifest-only removal while retaining its global behavior.
- Existing active-reference checks are fail closed but may not cover every reference class required here; scoped cleanup must add missing checks before it can be enabled.
- A UI operator can see file paths under the configured Work role, matching existing Housekeeping preview behavior. No arbitrary path is accepted from the client.

## Rollback

Rollback removes only the new routes/UI and stops issuing scoped cleanup. Existing persisted preview/evidence rows and already removed staging files remain as historical records; rollback does not recreate files, rewrite Dismiss state, or alter Validation/Result evidence.
