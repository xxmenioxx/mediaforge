## Context

See proposal.md for motivation. The repository already has one canonical
subtitle conversion contract in `openspec/specs/subtitles/spec.md`. Serena
inspection shows that the implementation currently separates:

- canonical resolved track decisions and `SubtitleArtifact` metadata;
- canonical bitmap OCR evidence and retained geometry in
  `generateBitmapSubtitleAtPathWithResult` / `generateSharedConvertedSubtitleArtifacts`;
- generated bitmap ASS output at the existing `renderBitmapASSCues` seam;
- native ASS/SSA structure parsing and source-preserving reconstruction at
  `parseTranslationASSDocument` / `ReconstructDialogueProviderTexts`;
- Asset Info's `subtitleExtractionOperation` registry, operation cancellation,
  staging, validation, cleanup, and publication barriers; and
- `AppSetting` list/upsert/validation through the existing settings handler.

Text conversion currently uses FFmpeg for extraction/rendering, while bitmap
conversion already fans one canonical cue/evidence result to SRT and ASS. The
design must extend these existing boundaries without adding a second subtitle
cue model, OCR path, ASS serializer, sidecar publisher, or operation system.

## Goals / Non-Goals

**Goals:**

- Define and persist a reusable style contract whose IDs are stable even when
  display names or appearance values change.
- Make the backend the authority for style validation, role/style resolution,
  color conversion, collision handling, frozen snapshots, and output behavior.
- Preserve native ASS/SSA structure by default and make explicit restyling
  narrow, opt-in, and reversible.
- Reuse #26 geometry as independent layout evidence and keep SRT neutral.
- Add safe single-sidecar Asset Info Restyle / Regenerate flows using exact
  source identity and the existing lifecycle/publication machinery.
- Keep the Settings preview fast and visibly approximate.

**Non-Goals:**

- #131 subtitle composition, batch restyling, AI style selection, a new OCR
  engine, translation changes, SRT styling, font download/attachment management,
  player-specific rendering guarantees, or video rendering for color picking.
- Automatic inference of a new `top` semantic role from geometry.
- Rewriting already-published sidecars merely because Settings changed.

## Decisions

### 1. One style contract, separate from cue and role data

Introduce one backend-owned conceptual `SubtitleStylePreset` contract. It is a
style definition, not a replacement for the canonical cue/document model. The
contract includes:

```text
id, displayName, primaryColor, outlineColor, shadowBackColor,
opacity, fontFamily, fontSizeOrAuto, bold, outlineWidth, shadowDepth,
alignmentBehavior, provenance
```

Built-ins are code-defined stable identities with persisted appearance
overrides. Custom IDs are generated by the backend using an opaque UUID-like
identity; display-name slugification is never an identity operation. The
normalized setting stores a bounded versioned object, for example:

```text
subtitleSettings: {
  generateSRTFallbackForASS: <existing field>,
  subtitleStyling: {
    version: 1,
    preserveSourceStyles: true,
    overrideExistingASSStyles: false,
    builtInOverrides: { ... },
    customPresets: [ ... ],
    savedColors: [ ... ],
    recentColors: [ ... ]
  }
}
```

This extends the existing `subtitleSettings` AppSetting rather than adding a
table. The settings handler validates and normalizes the whole styling object
before the existing upsert. A missing nested object is equivalent to defaults;
the existing SRT fallback field remains independently backward compatible.

### 2. Canonical color boundary is backend-only

The frontend edits `#RRGGBB` values and may normalize optimistically for user
feedback, but it never constructs ASS colors. The backend helper performs:

1. trim and validate `#` plus three or six hexadecimal digits;
2. expand three digits, uppercase, and store six digits;
3. validate opacity as a bounded percentage;
4. calculate ASS alpha with `round((100-opacity)*255/100)`; and
5. emit `&H` + alpha + blue + green + red + `&`.

The helper also parses its own canonical output for round-trip tests. Generated
styles use the three configured RGB colors consistently for the exposed ASS
color fields; any legacy/non-exposed generated field receives a deterministic
fallback. Native source color fields are not parsed and rewritten during the
default preservation path.

### 3. Role selection and layout resolution have distinct inputs and outputs

The style resolver accepts a canonical cue/document view containing:

- the already-resolved semantic role and its provenance;
- optional explicit operation style selection;
- existing canonical layout/geometry evidence;
- explicit position/movement/alignment metadata, if present; and
- source/native versus generated policy.

It returns style ID/definition separately from role, resolved alignment, and
optional exact position. The precedence is:

1. native source preservation, unless explicit override is enabled;
2. explicit operation style selection or an eligible canonical role mapping;
3. an existing explicit canonical layout/style hint, including a future-safe
   `top` hint where the canonical policy already provides one; and
4. configured `MVF_Default`.

For initial role mappings, `signs` maps to `MVF_Sign`; other existing roles use
their configured mapping or default to `MVF_Default`. `unknown` never becomes a
top note merely because geometry is upper-third. Geometry remains #26 layout
evidence and may resolve coarse ASS alignment, but it cannot reclassify the
semantic role or erase a valid explicit `\\pos`, `\\move`, or alignment override.
`MVF_Top` is therefore a stable selectable preset and explicit policy target,
not a second classifier.

### 4. Extend the existing ASS serializer seams, never create a parallel one

There are two existing responsibilities to preserve:

- `translationASSDocument` parses ASS/SSA Events and reconstructs only allowed
  dialogue text changes against the original source string. This is the native
  source-preserving document boundary and remains the path for native restyle.
- `renderBitmapASSCues` renders canonical bitmap cues with existing #26 coarse
  geometry. This is the generated ASS rendering seam and should be generalized
  or extended to consume the existing canonical cue representation plus a
  resolved style, rather than adding `subtitle_style_serializer.go` or another
  ASS document model.

For SRT-to-ASS, the implementation must route the existing canonical text cue
result through that same generated ASS rendering seam (or its current shared
equivalent) when configurable styling is requested. FFmpeg remains an external
conversion tool where the canonical plan requires it, but it must not become a
second source of style policy. The SRT serializer remains text/timing-only.

Generated styles are emitted once per distinct stable style snapshot and events
refer to deterministic namespaced names. Native source style blocks are copied
unchanged by default. Explicit override may append generated definitions and
change only eligible event style assignments; it never deletes or redefines
source styles and never rewrites inline structural tags.

### 5. Preserve source styles by policy, not by accidental parser behavior

The persisted defaults are `preserveSourceStyles=true` and
`overrideExistingASSStyles=false`. Native ASS/SSA restyle first validates the
selected exact document, captures its source revision, and uses the existing
parser/reconstructor so custom style names, event assignments, karaoke,
override tags, margins, layers, drawing mode, positioning, timing, and order
survive.

When override is enabled, the resolver computes event assignments from the
canonical role/policy. It appends collision-safe generated style definitions
under a namespaced name derived from stable preset and artifact identity. A
source style called `MVF_Default` remains source-owned; a configured MVForge
`MVF_Default` never changes its meaning. Inline `\\r` reset tags and other
override blocks are preserved even when the event's base Style field changes.

### 6. Keep `both` as one canonical transformation

The existing `generateSharedConvertedSubtitleArtifacts` path already creates
one canonical SRT staging result, performs bitmap OCR once when required, and
fans output to SRT and ASS. #123 keeps that operation and attaches the resolved
style snapshot only at ASS serialization. Geometry, canonical OCR evidence,
role metadata, and cue IDs are reused; no serializer starts OCR or parses a
second cue stream. A style edit never touches SRT bytes.

### 7. Use one versioned setting snapshot for mutable policy

At operation start, the backend reads and normalizes styling once, resolves a
bounded canonical policy snapshot, and records a version/hash in the operation
request/provenance. Queue uses the same snapshot at its existing preparation/
freeze boundary and stores it with the immutable resolved subtitle plan. Worker
execution never rereads mutable Settings. Snapshot data includes normalized
preset definitions and policy flags, not arbitrary UI payloads or secrets.

### 8. Asset Info is a single-sidecar adapter over the existing operation

The new entry point extends the existing Asset Info subtitle action surface and
uses the existing `subtitleExtractionOperation` status/cancel/poll contract.
The request is bound to an exact identity:

```text
source kind/path or embedded stream identity
source revision/fingerprint
representation and language
role/provenance
requested mode and target artifact identity
style policy/version
```

For an external sidecar, use the already selected validated path and its
revision; do not scan for a same-language sibling. For an embedded source, use
the media snapshot and stream signature already used by canonical planning.
Restyle ASS/SSA reads and serializes the existing document. SRT-to-ASS uses the
canonical text cue path. Bitmap regeneration delegates to the existing OCR
evidence/lifecycle only when its provenance says the source can be recomputed.

The initial operation is one selected sidecar. Batch restyling is deliberately
not an implied extension of this API.

### 9. Stage, validate, recheck, then publish a sibling

Each operation writes only to operation-owned staging, validates the exact
representation and canonical style/structure, and makes the result inspectable
before the existing subtitle publication barrier. The default target is a
deterministic sibling. If a sibling destination exists, reuse existing
collision-safe sidecar naming or report a deterministic conflict; never
overwrite it implicitly.

An explicit replace option uses the existing publication mutex, source revision
recheck, rollback backup, and atomic publication behavior already used by
subtitle operations. Cancellation is signaled through the existing context,
staging is cleaned with the existing bounded cleanup path, and a failed/cancelled
operation cannot remove source or previously published sidecars.

### 10. Reuse existing font attachment behavior

Native ASS/SSA attachment extraction/publication remains the sole font path.
Preserved native artifacts retain their attachment metadata. A custom generated
style stores only a font name and can show an evidence-based availability
warning; it does not download, bundle, or invent a fallback font. The browser
preview uses available browser fonts only as an approximation.

### 11. Settings UI is a local approximation

Add a subtitle styling card alongside the existing subtitle compatibility and
translation settings. It edits presets, palette values, preservation/override
policies, and a small preview surface in local component state, then submits one
normalized settings payload through the existing settings mutation. The preview
renders dark/light/mixed swatches and representative role labels without
calling FFmpeg or the backend subtitle operation. It explicitly notes browser
font, libass metric, outline, and scaling differences.

Asset Info exposes Restyle / Regenerate only for backend-authorized exact source
representations and displays the source identity, current policy, mode, and
override warning. Frontend eligibility is a projection of backend metadata; it
does not infer roles, source revisions, or output formats.

### 12. Keep #131 future-compatible without implementing it

The resolver API accepts stable style IDs and canonical role/layout inputs, and
the output style names are namespaced deterministically. Track Profiles are not
given duplicate style definitions in this change. Future composition can pass
its selected IDs and canonical merged cues through the same resolver/serializer
without inventing a composition-specific style model. No composition work is
performed now.

## Risks / Trade-offs

- **Risk:** Native ASS/SSA has heterogeneous syntax and legacy style formats.
  **Mitigation:** default to source-string-preserving parse/reconstruction,
  validate protected structure, and confine generated style insertion and
  assignment changes to explicit override mode.
- **Risk:** Extending the generated ASS seam could accidentally affect SRT or
  OCR lifecycle behavior. **Mitigation:** keep SRT serializer input/output
  text-and-timing-only, assert one OCR evidence identity for `both`, and test
  exact ASS chains for text and bitmap sources.
- **Risk:** A user-selected font is unavailable at playback. **Mitigation:**
  retain the name, surface warnings where runtime evidence exists, and reuse
  existing attachment handling without downloads or substitutions.
- **Risk:** Settings edits race with long OCR/regenerate work. **Mitigation:**
  capture a normalized immutable snapshot and version at operation/freeze time;
  never reread mutable Settings during execution.
- **Risk:** Restyle targets the wrong sidecar or overwrites current content.
  **Mitigation:** exact identity plus final revision check, sibling-by-default
  publication, explicit replace opt-in, and existing rollback barrier.
- **Risk:** Palette data grows in a NAS AppSetting. **Mitigation:** normalize,
  deduplicate, and enforce 32 saved/12 recent bounds before persistence.

## Migration Plan

1. Ship the additive validator/resolver and UI with missing styling settings
   resolving to safe defaults. Existing settings and artifacts require no
   database migration.
2. Add generated ASS integration and focused tests while leaving native ASS/SSA,
   SRT, translation, OCR, and existing fallback output unchanged by default.
3. Add the single-sidecar Asset Info operation using existing staged operation
   and publication infrastructure.
4. Existing native and generated sidecars are not rewritten automatically.
   Users opt into Restyle / Regenerate; replacing a sidecar remains explicit.
5. Rollback removes only the new style-policy consumers and UI. The existing
   subtitle pipeline continues with its prior default rendering and all existing
   artifacts remain readable.

## Open Questions

None. The remaining implementation choices are bounded by the contracts above
and can be verified with focused tests without changing the specification.
